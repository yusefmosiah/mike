# Research: OpenClaw computer use, and Linux-VM-plus-host-helper architecture
Date: 2026-10-25. Tags: [V] read from a primary source this session (docs/repo/vendor page); [R] secondhand (blogs, news, search summaries); [K] my prior knowledge, unverified this session.

## 1. OpenClaw

### 1.1 What it is [V]
- Open-source, self-hosted personal AI agent: one Gateway process on your machine connects chat channels (WhatsApp, Telegram, Slack, Discord, iMessage, Signal, Teams, 20+) to an agent runtime. Repo https://github.com/openclaw/openclaw: MIT, ~393k stars, ~82.6k forks at fetch time. Stewarded by "OpenClaw Foundation", an independent 501(c)(3); "no paid tier, hosted service, or token".
- Name history [R] (https://en.wikipedia.org/wiki/OpenClaw, https://openclaw.academy/blog/complete-history-of-openclaw-naming-journey/): Warelay -> Clawdis -> Clawdbot (Jan 2026) -> Moltbot (after an Anthropic trademark notice) -> OpenClaw (~Jan 29-30, 2026). Creator Peter Steinberger (ex-PSPDFKit, also author of Peekaboo) joined OpenAI ~Feb 14, 2026; project moved to a foundation. One blog claims a "GNU 3.0" license; the repo says MIT, trust the repo [V].
- So the product owner's name is right: it is the former Clawdbot/Moltbot. Docs still carry legacy socket symlinks named clawdbot/clawdis/moltbot [V].
- Requires Node 24.16+ or 26.1+ (docs/README as fetched) [V]; native apps for macOS, iOS, Android, Windows, Linux.

### 1.2 Architecture: Gateway + nodes [V] (https://docs.openclaw.ai/nodes, /gateway/pairing, /gateway/protocol/*)
- Gateway = control plane for sessions, tools, channels, models. Design principle on README: "trusted gateway, untrusted execution, policy enforced by code".
- A **node** is a companion device (Mac, iPhone, Android, Windows, Linux, headless host) that connects to the Gateway over **WebSocket** with `role: "node"` and exposes command namespaces invoked via `node.invoke`: `camera.*`, `screen.*`, `system.run`, `system.notify`, `location.get`, `device.*`, `canvas.*`, `computer.act`, plus browser/skill/MCP commands via the CLI node host. Nodes are peripherals; channel messages never arrive at a node.
- Remote gateway: SSH tunnel with loopback bind, Tailscale Serve, Bonjour discovery. The macOS app has a "remote control" flow. Phone -> Gateway -> node is exactly this model; Android/iOS apps are themselves nodes (and chat clients).
- "Cloud Workers/Sessions": session work dispatched to paired devices or throwaway cloud machines while the Gateway keeps transcript, workspace, credentials; inference proxied through the Gateway so provider keys stay off the worker; per-dispatch minted credentials; owner-epoch fencing; workers cannot call operator RPCs (https://docs.openclaw.ai/gateway/cloud-workers/security-model). Caveat in same page: processes running as the worker's OS user can read worker state; "Codex managed workspace is not an OS sandbox"; provider egress not restricted.

### 1.3 Pairing and auth model [V] (https://docs.openclaw.ai/gateway/pairing)
Two separate layers stored on the device record in the Gateway SQLite DB:
1. Device pairing (role `node`) gates the WebSocket `connect` handshake. Device = ID + public key; key change never auto-approved; pairing requests expire in 5 min. Setup links `oc-pair://` carry a single-use bootstrap token (10 min), separate from the resulting device token. Device tokens rotatable/revocable (`openclaw devices rotate`).
2. Capability approval (`node.pair.*`): a node declares commands; any new/widened set creates a pending request that grants nothing until an operator approves. Scopes: `operator.pairing`, plus `operator.write` for ordinary commands, plus `operator.admin` for sensitive ones (`system.run`). Since 2026.3.31 commands stay disabled until approved; queued ones dropped.
- Auto-approve paths: silent loopback, SSH-verified (Gateway SSHes to host, compares device key), trusted CIDR (first command surface still manual).
- Then command policy: per-platform default allowlist, dangerous commands opt-in under `gateway.nodes`, global deny `gateway.nodes.commands.deny`, exec allowlists, exec approval prompts on the Mac.
- Windows node mode needs "two separate approvals: device connection and command surface" [V] (docs /platforms/windows).
- Trust boundary (https://docs.openclaw.ai/gateway/security/trust-model) [V]: one trust boundary per Gateway (one operator or mutually trusting team); NOT a hostile multi-tenant boundary; anyone who can edit `~/.openclaw` is an operator; in the default single-operator mode host exec on gateway/node runs without approval prompts "intentionally"; prompt-injection-only chains are out of scope for vuln reports. Defaults: Gateway binds loopback on host installs; unknown DM senders get a pairing code; container images default to exposed bind.

### 1.4 macOS computer-use architecture [V]
Source pages: https://docs.openclaw.ai/nodes/computer-use, /platforms/macos, /platforms/mac/peekaboo, /platforms/mac/xpc.
- Shipped helper: **OpenClaw.app**, a menu-bar app that is the single Gateway connection and node identity for the Mac. It runs the node-host runtime internally; hosts a native `openclaw-mac` helper CLI; prompts TCC (screen recording, mic, speech, automation, accessibility). Approved shell commands run in the app's context so they inherit its TCC attribution. Bundle ID must stay stable/signed so TCC grants persist (docs /platforms/mac/xpc, /signing).
- One built-in `computer` tool (needs a **vision-capable model**) with `computer.act` + `screen.snapshot` contracts, same on Gateway desktop, paired node, cloud session.
  - Perception: `screenshot` returns a `frameId`; coordinate actions must reference the latest frame (provider maps pixels to display points). Window observations return `observationId` + element refs (accessibility-derived). Screenshots are model-only, never sent to chat; unchanged screen returns metadata not an image. Browser state (CUA only) via opaque `browserRef`/`pageRef`.
  - Actions: click/double/triple, move, drag, mouse down/up, scroll, type, key, hold_key, wait; window/element/browser actions only if the provider advertises them (no emulation, no per-action fallback between providers).
  - Backends: **Peekaboo** (macOS default, in-process, coordinate actions) or **CUA driver** (daemon embedded in OpenClaw.app, inherits its permissions) selectable in the app. On Windows (x64/ARM64) and glibc Linux (x64/ARM64): experimental `@openclaw/cua-computer` plugin calling the pinned CUA Driver SDK. Linux Gateway desktops use a managed X11 display; native Wayland rejected. Also related paths: "Codex Computer Use" plugin and direct `cua-driver` MCP.
  - Gates (all must hold): tool policy exposes `computer`; vision model; node advertises commands and pairing update approved; node-local "Allow Computer Control" (macOS default ON); OS permissions (Accessibility + Screen Recording, plus Event Posting for Peekaboo).
  - **No per-action confirmation** once enabled+approved. Native approval panels are hidden from snapshots and input refused while one is pending (explicitly "hardening, not an isolation boundary"). Docs: "Treat all on-screen content as untrusted input" and don't combine ask-mode exec with unrestricted computer use for untrusted models.
- **PeekabooBridge** (https://docs.openclaw.ai/platforms/mac/peekaboo) [V]: OpenClaw.app hosts a local UNIX socket at `~/Library/Application Support/OpenClaw/<socket>`; standalone `peekaboo` CLI connects and runs UI automation under the app's TCC grants. Bridge verifies caller **code signature** (only the official Peekaboo-signed CLI; same UID or same team not enough); 10 s request timeout; snapshots in-memory 10 min/max 50. Client host preference: Peekaboo.app, Claude.app, OpenClaw.app. The built-in `computer` tool does not use this socket (in-process).
- Other IPC [V]: exec-approvals Unix socket (mode 0600, token, `getpeereid` peer-UID, HMAC-SHA256 challenge, short TTL); `~/.openclaw/mac-control.sock` (JSONL, nonce+timestamp+HMAC, 15 s TTL, token file 0600). Doc says all sockets local-only. (No XPC despite the URL name.)
- **Peekaboo** (https://github.com/steipete/Peekaboo) [V]: MIT, v4.9.7, macOS 15+; `see` returns a structured UI map (AX tree element IDs) plus screenshots, optional VQA; click/type/press/scroll/drag/set-value/menu/dock/dialog/window/space; can target a window ID so input runs in the background; also an MCP server; `peekaboo agent` for NL tasks. Needs Screen Recording + Accessibility (+ synthetic-input permission).
- **Cua / cua-driver** (https://github.com/trycua/cua) [V], ~31k stars: Cua Driver inspects/operates native apps and browsers on macOS/Windows/Linux via CLI/MCP/SDK with "background delivery" (no cursor move, no focus steal where supported); mechanism not documented on the pages I could fetch (embedding contract file `rust/Skills/cua-driver/EMBEDDING.md` is the place to look). Permission modes `standard`/`bounded` (reviewed manifest)/`unrestricted` (needs `--dangerously-bypass-approvals`); attaching to a logged-in Chromium profile needs explicit `--grant existing-profile`. Optional `cua-perception` (OmniParser icon detector) is AGPL-3.0. Repo is mostly MIT; Cua Spaces/Driver Bench are FSL-1.1-MIT. Same repo ships **Lume** (macOS+Linux VMs on Virtualization.framework) and gVisor-based sandbox SDK; `cuabot` deprecated "known security issues".
- Browser: separate `browser` tool using a managed dedicated "openclaw" Chrome profile by default; "Chrome MCP existing-session" and an extension relay can act as the user across their real profile. Docs warn this "is not safer" and recommend a dedicated profile with sync/password manager disabled (https://docs.openclaw.ai/gateway/security/browser-control) [V]. SSRF policy blocks private networks by default but is explicitly "not a complete firewall".

### 1.5 Windows / Linux [V]
- Windows (https://docs.openclaw.ai/platforms/windows): "Windows Hub" native WinUI companion (Win10 20H2+/11) recommended; provisions an app-owned WSL Gateway; registers as a node (screenshots, notifications, controlled exec; screen record/camera opt-in). Tauri app as backup; native CLI/Gateway via PowerShell; WSL2 most Linux-compatible. Hub can also run a loopback MCP server for local Claude Desktop/Cursor.
- Linux (https://docs.openclaw.ai/platforms/linux): Gateway fully supported; Tauri tray app (X11 shortcuts only; Wayland partial); "desktop sharing" = authenticated local VNC; linux-node plugin with notifications, optional camera/location. Computer use on Linux = CUA plugin on X11.
- Practical read: macOS is clearly the best-supported computer-use host; Windows/Linux are real but newer/experimental.

### 1.6 Models [R/V]
- Model/provider layer is plugin-based; Claude, Codex/OpenAI, Gemini and local servers (Ollama, vLLM, LM Studio, llama.cpp) supported [V: README and doc index].
- Computer use needs a vision-capable model [V]. Community guides name Qwen 3.x (27B class, ~18-20 GB), Qwen3-Coder, GLM-4.7/5.x, Kimi K2.5, Llama 3.3 70B as common open picks [R] (https://haimaker.ai/blog/best-models-for-clawdbot/, https://rentamac.io/best-local-llms-openclaw/). These are SEO-grade blogs about general agent/tool use; **no source I found benchmarks open models on screenshot-grounded GUI control with OpenClaw**. Cua ships its own small CUA-S1 models (forms) [V]. Treat open-model computer use as unproven; use accessibility/structured refs rather than raw pixel grounding where possible.

### 1.8 Copy vs avoid
Copy:
- Gateway/node split with node as a capability-declaring peripheral; two-step approval (connect vs command surface); public-key device identity; single-use short-lived bootstrap link/QR; revocable device tokens; pending requests that grant nothing.
- Host app that owns TCC grants and brokers a local socket with peer-credential + code-signature checks; stable signed bundle ID.
- Frame-ID discipline (coordinate actions must reference latest screenshot), element refs from AX tree, "omit unsupported actions rather than emulate", hidden/refused input while an approval dialog is up, per-capability kill switch and global deny list.
- Inference proxied via the gateway so provider keys never sit on the worker.
Avoid:
- Default "no per-action approval once enabled"; host exec without prompts by default; auth token in URL; gateway reachable via a web page the user visits; unvetted community skill registry running with host privileges; single trust boundary assumption (we are multi-tenant by nature: server holds many users); Node 24/26 runtime dependency on user machines; prompt-injection treated as out of scope.

## 2. Linux VM in the desktop app + host-side helper

### 2.1 Existing precedent for "agent in VM"
- **Claude Cowork** [V partly]: Anthropic engineer on HN (https://news.ycombinator.com/item?id=47220118): Claude Code harness runs "inside a Linux VM" with "additional sandboxing, network controls, and filesystem mounts", using Apple's virtualization framework or Microsoft's Host Compute System (Windows). Reasons: a computer to write software that isn't the user's, hard boundary guarantees, less approval fatigue. Reverse engineering [R] (https://aaddrick.com/blog/claude-desktop-cowork-mode-vm-architecture-analysis, https://pluto.security/blog/inside-claude-cowork-how-anthropics-autonomous-agent-actually-works/, https://blog.jimmyvo.com/posts/claude-coworks-virtualization/): Swift native addon over Virtualization.framework, ARM64 Ubuntu 22.04, ~10 GB rootfs image, bubblewrap inside the guest, VirtIO shares with path translation, 8 GB default RAM; an escape write-up exists (https://accomplish.ai/blog/sharedroot-escaping-claude-cowork-sandbox/). Notably, **host computer use is a separate path with no sandbox**: help center (https://support.claude.com/en/articles/14128542-let-claude-use-your-computer-in-cowork) [V] says "Computer use has no sandbox between Claude and your applications"; tool preference is connectors, then browser (built-in or Claude in Chrome), then screen; per-app approval prompt, first-use full-screen prompt per session, background windows by default on macOS 15+, default-blocked sensitive app categories (trading/crypto), Mac+Windows beta for Pro/Max. This is literally the VM-for-work + host-for-computer-use split we are considering.
- **Docker Sandboxes (`sbx`)** [V] (https://www.docker.com/blog/why-microvms-the-architecture-behind-docker-sandboxes/, Jan 30 2026): per-agent microVM with own kernel; custom VMM on Hypervisor.framework (macOS), WHP (Windows), KVM (Linux); Firecracker rejected because Linux-only; private Docker daemon in VM; file access scoped; **outbound traffic through a host-side policy proxy that injects credentials so keys never enter the VM** [R from third-party summary; Docker itself says proxy is not hermetic]. Best template for the broker's network side.
- **OpenClaw sandboxing** [V]: Docker/Podman/SSH/OpenShell/Crabbox backends sandbox exec/file tools and an optional browser; Gateway and `tools.elevated` stay on host; docs don't say computer use is sandboxed. Same split.
- **Cua** [V]: Lume macOS/Linux VMs via Virtualization.framework + Cua Spaces desktops for agents; also host-side Cua Driver. **E2B** (Firecracker, [R]), Modal (gVisor, [R]) for cloud sandboxes (https://fly.io/learn/firecracker-vs-gvisor/).
- **Codex CLI** local sandbox: Seatbelt on macOS, restricted tokens on Windows [R].

### 2.2 Mac VM options
- **Virtualization.framework (VZ)** [V via Apple repos]: native, Apple silicon Linux guests, virtio-blk/net/fs/vsock (`VZVirtioSocketDevice`), Rosetta for x86 Linux userland. Entitlement `com.apple.security.virtualization` [R/K]. App Store sandbox is workable for VZ but awkward: forum reports of sandbox extension failures, no easy guest IP discovery, bridged networking needing `com.apple.vm.networking` (restricted) (https://developer.apple.com/forums/thread/822025, /786363). vsock under App Store sandbox: **not verified**. Practical: ship Developer ID + notarized outside the MAS; Docker Desktop, Lima, Tart, OrbStack, Cowork all distribute that way [K].
- **apple/containerization + apple/container** [V] (https://github.com/apple/containerization, https://github.com/apple/container/releases): Swift package, Apache-2.0, needs Apple silicon + macOS 26 + Xcode 26; one lightweight VM per container; guest init `vminitd` exposes **gRPC over vsock**; virtio-fs shares (documented for Linux backend), Rosetta for amd64, dedicated IP per container, custom kernels (tested from 6.14.9); "sub-second start" is Apple's claim, no measurements. The `container` CLI reached 1.0 by ~Jul 2026 and was at 1.6.1 on Oct 23, 2026 (release page, years omitted). Best fit for "embed a VM runtime in a Swift/Mac app": reuse `vminitd` and its vsock gRPC instead of inventing an agent. Constraint: macOS 26 only; Intel not supported.
- **Lima** [V partial]: Apache-2.0, CNCF incubating, vz driver with vzNAT (macOS 13+), file sharing and port forwarding. Good if you want to shell out to an existing tool; heavy to embed.
- **Tart** [V partial]: Cirrus Labs, Virtualization.framework, macOS and Linux guests, "fair-source" license (terms not confirmed, check before embedding).
- **OrbStack**: proprietary, closed; not embeddable. Reported cold start ~1.8-5 s [R] (https://thesisbench.com/utm-vs-orbstack-vs-lima-macos-vm-real-cold-start-disk-i-o-and-memory-numbers-on-m3-macbook-pro/: OrbStack 1.8 s, Lima 4.6 s, UTM-VZ 11.2 s to SSH prompt; single unverified benchmark site).
- **UTM**: QEMU or VZ front-end for end users; not an embedding story [R].
- Footprint: rootfs ~10 GB in Cowork [R]; RAM is VM-reserved (Cowork default 8 GB [R]); Apple's container claims sub-second start. Budget a minimal image (Alpine/Debian slim + Chromium-less toolset) and balloon/free-page reporting; I did not find verified numbers.

### 2.3 VM -> host channel
- vsock: VZ `VZVirtioSocketDevice`; guest uses AF_VSOCK; host listener per port. Apple's `vminitd` already uses this [V]. Authentication is by VM identity (the host knows which VM the connection came from since the listener is attached to a specific VM object), no network exposure, no IP discovery needed. Preferable to TCP-over-NAT (bypasses firewalls/VPNs, avoids sandbox network entitlements).
- Windows: Hyper-V sockets `AF_HYPERV` (host) <-> `AF_VSOCK` (guest); service GUID template encodes the port, service must be registered under `HKLM\...\GuestCommunicationServices` [V] (https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/user-guide/make-integration-service). Registry write needs admin once at install. WSL2 exposes this to Linux distros; custom distro per app is possible. Windows Sandbox: no data retrieved (disposable, needs Pro/Enterprise per my memory [K]; not suitable for a persistent agent VM). Cowork uses the Host Compute System (HCS) on Windows [V via HN].
- Linux: Firecracker (KVM, vsock, ~125 ms boot, <5 MiB overhead claims [R]), cloud-hypervisor (hybrid vsock, virtiofsd; used by Apple's containerization Linux backend [V]), gVisor (userspace kernel, no hardware virt needed, syscall overhead [R]), bubblewrap (namespaces, weakest, but unprivileged; Cowork uses it inside the VM [R]). On a user's Linux desktop the host *is* Linux, so the VM matters less; bwrap/Landlock plus a broker socket is the pragmatic default, microVM for strong mode.
- Shared folders: virtio-fs (VZ `VZVirtioFileSystemDeviceConfiguration`), mount only chosen directories, read-only by default; Cowork and Docker both scope mounts [V/R]. Beware symlink/path-translation escapes (the Cowork "SharedRoot" write-up [R]).

### 2.4 Broker/policy enforcement (so a compromised VM cannot drive the host)
Design principles supported by sources:
1. The VM has no ambient host authority. Its only door is one vsock RPC endpoint served by the (signed, TCC-holding) host app. Docker: "credentials never cross the VM boundary", host-side proxy [R]. OpenClaw: tool authority and credentials minted/held by Gateway, worker cannot call operator RPCs [V].
2. Capability-typed, narrow RPCs (not "run arbitrary AppleScript"): `screen.snapshot`, `computer.act` with frameId, `browser.*` with per-origin grants, `fs.read(mount)`. Unsupported = absent (OpenClaw [V]).
3. Policy lives on the host in code: per-app allowlist (Cowork asks per app and blocklists categories [V]); per-session grants; rate limits; high-risk action classes (forced quit, downloads, recording, purchases, credential entry) always require a human approval delivered out-of-band to the phone (OpenClaw calls these "high-risk" [V]; Cowork says safeguards "aren't absolute" [V]).
4. Approval UI must be unforgeable by the agent: native panel hidden from screenshots and input refused while pending (OpenClaw [V]); on our side, approvals via phone push, not on-screen.
5. Identify the caller: code-signature verification and peer-UID checks on any local socket (OpenClaw/Peekaboo [V]); vsock removes the need for most of this but add a per-session token minted by host at VM start and bound to session.
6. Audit log of every brokered action (host-side, append-only; Cua "Computer History" stores metadata only [V]).
7. Treat screen content/page content as untrusted input; avoid combining unattended mode with an untrusted/open model (OpenClaw docs [V]).
8. Honest limits: Cowork's own sandbox was escaped via a kernel bug in a published write-up [R]; the VM boundary reduces, not removes, risk; the broker is the real security perimeter.

### 2.5 "Looks like a normal user": operating the user's own machine
Framing: the agent acts as the user on the user's own devices, accounts, network; no third-party security controls are being circumvented by design. What signals exist:
- Network/identity: residential IP, real device fingerprint, long-lived cookies, real TLS stack, real Chrome version and extensions arrive for free if the host browser does the work. A browser inside a Linux VM would present a Linux UA, VM GPU, different fonts, NAT egress; so run browsing on the host, not in the VM. [K]
- CDP caveats [V]: Chrome 136+ ignores `--remote-debugging-port`/`--remote-debugging-pipe` on the default profile (https://developer.chrome.com/blog/remote-debugging-port, Mar 17 2025) as an anti-infostealer measure; need non-default `--user-data-dir` (separate profile, loses the user's cookies) or Chrome for Testing. The supported route to the user's live profile is the user-toggled remote debugging at `chrome://inspect` plus a consent dialog per client connection (Chrome DevTools MCP `--autoConnect`, Chrome ~M144, Dec 2025) [R] (https://github.com/ChromeDevTools/chrome-devtools-mcp/issues/825, Qwen Code issue #8737: dialog re-appears each session, no "remember" yet). Implication: reliable CDP on the real profile requires a user-visible grant. Alternative: a browser extension (like Claude in Chrome [V help center mentions it], OpenClaw extension relay [V]) which acts inside the real profile with Chrome's own extension permission model.
- Automation fingerprints [R/K]: `navigator.webdriver` is true whenever Chrome runs with a remote debugging port, including attach to existing browser (https://docs.rs/crate/glass-browser/0.2.4/source/docs/detection-surface.md); `Runtime.enable` side effects; headless UA/flags. CDP `Input.dispatch*` events carry `isTrusted=true` but the CDP session itself leaves traces [K]. Extension-driven and OS-level input produce no webdriver flag.
- OS-level input [K]: CGEvent posts are real HID-level events to the page (isTrusted true); in-process detectors on the Mac can see event source state IDs and tap points, but web pages cannot. Timing: perfectly regular intervals, instantaneous teleporting cursors, zero scroll inertia are the behavioral signals pages and fraud vendors use. Cua's "background delivery" avoids moving the user's real cursor [V claim only].
- Position: do not engineer evasion. Prefer official APIs/connectors first (Cowork's order: connectors, then browser, then screen [V]), disclose automation where a site's terms require, honor robots/ToS, keep human-in-the-loop for logins/captchas/payments. Operating the user's own signed-in browser in a visible window is simply the user's session; if a site blocks it, that is the site's policy to respect.

## 3. Recommended architecture sketch
Phone (our app) <-TLS/WS-> Server agent (model orchestration, memory, per-user creds) <-outbound WS, device-key authed-> Desktop app (Mac first).
Inside the desktop app:
- **Host process (signed, notarized Developer ID, owns TCC)**: connection manager (outbound only, like an OpenClaw node: device keypair, single-use QR bootstrap, two-step approval: device then capability set, revocable), VM manager, broker, local audit log.
- **VM (Linux guest on Virtualization.framework; evaluate apple/containerization `vminitd` for macOS 26+, else own minimal VZ launcher)**: runs the agent's shell/files/code tools. No NIC, or NAT with host-side policy proxy; credentials injected by host. Mounts: explicit virtio-fs folders, read-only default.
- **vsock RPC (host listener per VM)**: typed capabilities only: `computer.snapshot/act` (frameId, AX refs), `browser.*`, `fs.pick`, `notify`. Per-session token. Everything not declared is absent.
- **Host browser path**: prefer Chrome extension (user-installed, scoped to tab group / selected tabs like OpenClaw's relay) or the user-approved `chrome://inspect` grant; fall back to dedicated agent profile. Browsing never happens inside the VM, so IP/fingerprint/cookies are the user's own.
- **Computer-use executor**: AX-tree + screenshot, background (non-focus-stealing) input where possible; evaluate Peekaboo (MIT) or cua-driver (MIT core; read EMBEDDING.md) as embedded libraries rather than writing from scratch.
- **Policy engine**: per-app and per-origin allowlists, high-risk action classes always routed to phone approval (push), kill switch, global deny list, rate limits, append-only audit.
- Windows: same shape with HCS/WSL2 + AF_HYPERV (one-time admin registry registration) and UI Automation for AX; Linux: bwrap/Landlock or Firecracker/cloud-hypervisor + unix socket broker, X11 first.
Build order: (1) node protocol + pairing + broker without VM, host-only with approvals; (2) VM for tool execution; (3) harden (signature checks, audit, kill switches); (4) Windows/Linux.
